---
description: Show the Readback board for this branch, a commit, or a range
argument-hint: "[init | check | plan | deck | fill-me | stats | <range>] [--card] [--for dev|senior|lead|manager] [features|parts] [change|risk|money|owner] [--as pm|finance|support|design] [--format term|md|html|widget|slack|trailer]"
allowed-tools: Bash(sh "${CLAUDE_PLUGIN_ROOT}/scripts/rb" *)
---

Run Readback with the user's arguments and show the result.

- If `$ARGUMENTS` starts with `init`, run `sh "${CLAUDE_PLUGIN_ROOT}/scripts/rb" init`, then read `.readback/map.json`, fix tiles whose names are not product words (rename them the way a PM would say it). If the features level has fewer than 3 or more than 16 tiles, redraft it from the app's screens, routes or pages (one tile per thing a user can do, merging near-duplicates), with `owns` globs that match real files, then run `sh "${CLAUDE_PLUGIN_ROOT}/scripts/rb" check`. Tell the user in two lines what to check.
- If it starts with `stats`, run `sh "${CLAUDE_PLUGIN_ROOT}/scripts/rb" stats` and paste it in a code block. Then add one sentence on the gate that is furthest off (plans corrected under 20%, planned tiles that changed 90%+, questions per session going down), or say there is not enough data yet.
- If it starts with `check`, run `sh "${CLAUDE_PLUGIN_ROOT}/scripts/rb" check` and summarise the coverage in one line. If it lists "Largest shared files", ask the user which feature owns each one (AskUserQuestion if you have it, one question per file, the likeliest feature first and "shared" as an option; otherwise ask in plain text). For each answer run `sh "${CLAUDE_PLUGIN_ROOT}/scripts/rb" own <path> <feature-id|shared>`. If it lists "Owned by one feature, drawn by others", ask once per file whether to keep the owner or mark it shared (the suggested `--by` list first); for shared, run the `own ... shared --by ...` line it prints.
- If it starts with `plan`, map the current plan to tiles yourself (only the tiles the plan says it will change). Put the ones you are sure of in `--tiles` and the ones you are only partly sure of in `--maybe`, and write the "About to change" card JSON (the schema is in `rb.py`'s hook text: headline, risk, items, and optional outside, flow, reach, before_after, acts, keep), then run `sh "${CLAUDE_PLUGIN_ROOT}/scripts/rb" plan --tiles id1,id2 --maybe id3 --card -` with the card on stdin. Put tiles the plan says must not change in `keep`. If you have a visual tool (show_widget), run `plan --show --format widget` and pass its output to it unchanged; otherwise paste the card it prints, unchanged (every line, including any `?` question). If it shows maybe tiles or a "usually changes with" question, ask the user once, then rerun with `--tiles` set to the final list. For a page, add `--format html --out .readback/plan.html`. Readback never guesses the plan from keywords, and the opening request is not a plan: without a mapped plan (plan mode or a PR body) it shows no "unplanned" or "not touched" flags.
- If it has `--card` (or the user asks what changed against the plan), run `sh "${CLAUDE_PLUGIN_ROOT}/scripts/rb" show --card $ARGUMENTS`: the "What changed" card, the plan card checked against the diff. With show_widget add `--format widget` and pass the output unchanged; otherwise paste the term card in a code block.
- If it starts with `deck`, the user has many ideas (a file, a doc, a list in chat). Write one "About to change" card JSON per idea with an extra `"title"` (for more than ~10 ideas, split the writing across subagents on a small fast model), and run `sh "${CLAUDE_PLUGIN_ROOT}/scripts/rb" deck add -` with a JSON list on stdin, then `deck prep` and paste its summary. Then go one card at a time: run `deck next` (with show_widget: `deck next --format widget`, pass it unchanged, and wait: its buttons send "Readback deck: idea N → build|later|drop|merge"; without it, paste the term card and ask with AskUserQuestion, options 1 Build, 2 Later, 3 Drop, 4 Merge). Record each answer with `deck decide N <choice>` (add `--into M` for a merge when the card names no twin); it prints the next card. When it says the deck is done, run `deck summary` and show it the same way. If the user picks an idea to start, run `deck plan N`.
- If it starts with `fill-me`, run `sh "${CLAUDE_PLUGIN_ROOT}/scripts/rb" gaps` and paste it. If it says some questions could not be sorted, run `gaps --unsure`, label each with `gaps --label ID kind` (never repeat the question text anywhere else), and rerun `gaps`. Then run `brief`, write `.readback/context.md` as it says, in your own words from the code (never quote a prompt), run `brief --show` and ask the user to review it like the map.
- `--for dev|senior|lead|manager` picks the reader (pass it through when the user names who will read it). `--as ROLE` picks the role's lens and its default reader.
- When you write a pull request description, end it with a line `Readback-Plan: Tile name, Tile name` naming the tiles the PR sets out to change; CI uses it to flag unplanned and missing work, and checks claims like "no money impact" against the diff.
- If `--format html` is asked, add `--out .readback/board.html` and tell the user the path.
- Otherwise run `sh "${CLAUDE_PLUGIN_ROOT}/scripts/rb" show $ARGUMENTS` and paste its output inside a code block, unchanged. Then add at most one sentence: anything surprising (an unplanned tile, a planned tile left untouched, "No product change", or unmapped files).

Do not re-explain the key; the board carries it.
